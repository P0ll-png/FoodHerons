# Admin approval, vendor revenue PDF, and GCash-gated pre-orders

Three features land across the full stack on `feature/admin-revenue-gcash`: admin store approval (new `vendor_approval_status` enum + RLS narrowing + Admin panel controls), a client-side vendor revenue PDF (jsPDF, dashboard-triggered), and GCash-gated pre-orders (two new pre-queue order states, a `submit_payment` RPC, a private Storage bucket for proofs, and vendor/admin verification surfaces). The DB work is confined to three new migrations (0008/0009/0010) with 0001–0007 untouched; the C# order service stays the sole writer of `orders`; the frontend reuses existing tokens and the Icon set. Build is green (`dotnet build` 0/0), tests pass 108/108 (78 baseline + 30 new), and `npm run build` succeeds.

Watch for: the `publicVendors` filtered list is derived and exported in `VendorContext` but **consumed nowhere** — `Home.jsx` and `Search.jsx` still read the full `vendors` list, so non-approved stores remain visible in the student directory, category results, hero stats, and search (confirmed). This is the central behavioral promise of the admin-approval feature and it is not wired into the two discovery surfaces, only into the store page.

**Verdict**: NEEDS_CHANGES

## High-level view

The admin-approval story is correct at every layer except the two student discovery surfaces. The DB narrows the `vendors` SELECT policy so anon/students only read approved stores, `guard_vendor_columns` makes `approval_status` admin-only, and the Admin panel drives approve/reject/suspend/re-activate through the admin RLS UPDATE path. `VendorStore.jsx` forces `canOrder = false` for a non-approved store. But `Home.jsx` and `Search.jsx` were never switched from `vendors` to `publicVendors`, so the directory and search still list pending/rejected/suspended stores. The RLS narrowing masks this for a pure anon session, but any admin or owner session (whose RLS branch returns non-approved rows) will see them in the public directory, and the client-side filter that was designed to prevent exactly this is dead code.

The GCash pre-order machine is coherent and authorized server-side. `OrderService.Legal` (9 pairs) mirrors the SQL `transition_order` whitelist exactly, the sync test pins both, and the new states (`awaiting_payment`, `payment_submitted`) have no legal path to `preparing`/`ready`/`completed`. Authorization lives at the endpoint: `PaymentReview` is vendor-owner-or-admin, `StudentCancel`'s admin allowance is correctly scoped to the two pre-payment from-states only, and the student payment submission checks ownership plus an authoritative `screenshotPath` route-id prefix. The private `payment-proofs` bucket has both INSERT and SELECT policies keyed off the order-id path segment, with the vendor-owner SELECT branch joined through the order's own `vendor_id` so no vendor can sign another vendor's proof.

The revenue PDF is a pure, client-side module scoped by existing owner RLS. Every completed row now carries a canonical `placedAt`, so day-grouping keys off a real calendar date rather than "days ago", and the PDF prints its day-boundary basis.

Both READMEs are updated: the root drops "cash on pickup"/"no approval step" and adds the `/admin` row and GCash/PDF notes; `supabase/README.md` documents the 0008→0009→0010 apply order with the 0009-runs-alone constraint and the hosted-`storage` prerequisite. Palette is orange/yellow/white with no blue introduced in the new CSS.

### publicVendors is dead code; discovery surfaces still list non-approved stores

`VendorContext` derives and exports exactly what the design asked for:

```js
const publicVendors = useMemo(
  () => vendors.filter((v) => v.approvalStatus === 'approved'),
  [vendors]
)
```

and keeps `getVendor`/`currentVendorId` pinned to the full `vendors` list (the pinned invariant for the in-flight payment path, correctly honored). But a workspace-wide search for `publicVendors` outside the context file returns zero hits. `Home.jsx` reads `const { vendors, categories, locationAreas } = useVendors()` and uses `vendors` for `openCount`, `categoryVendors`, the hero `{vendors.length} vendors` stat, and the directory `VendorResults list={vendors}`. `Search.jsx` reads `const { vendors, categoryName } = useVendors()` and uses `vendors` for both `results` and `popular`.

The effect depends on session role because the RLS SELECT policy is `approval_status = 'approved' or owner_id = auth.uid() or auth_role() = 'admin'`:

```
anon / plain student session   -> RLS returns only approved rows -> directory happens to look correct
admin session                  -> RLS returns ALL rows           -> directory lists pending/rejected/suspended stores
vendor owner session           -> RLS returns approved + own row  -> own non-approved store shows in the public directory
```

So the client filter is not redundant with RLS — it is the layer that was supposed to keep non-approved rows out of the student-facing surfaces regardless of who is signed in. With it unwired, AC1 ("a freshly signed-up vendor's store does not appear in the directory, search, or as orderable on its store page") and AC4 (suspend removes from directory on next load) fail for any admin/owner session, and the derived list is dead code. The fix is mechanical — swap the student-facing reads to `publicVendors` in the two files, matching what `VendorStore.jsx` already does via its `approvalStatus` gate.

### Transition machine and its authorization are in sync and fail-closed

`OrderService.Legal` holds the 9 pairs and the SQL `transition_order` whitelist in `0010` lists the same 9 verbatim; `LegalTransitionSet_matches_sql_whitelist` asserts `OrderService.PlanTransition` accepts every SQL pair and rejects the pre-payment skips (`awaiting_payment→preparing`, `payment_submitted→ready`, `awaiting_payment→completed`). No pair reaches `preparing`/`ready`/`completed` from a pre-payment state, so an unverified order cannot enter the active queue (FR3.6/AC9/AC10).

Authorization is decided server-side in `TransitionAsync`, not hidden in the UI:

```
StudentCancel  -> student owner OR vendor owner OR (admin AND from in {awaiting_payment, payment_submitted})
PaymentReview  -> admin OR vendor owner
VendorAction   -> vendor owner
```

The admin cancel allowance is correctly scoped to the two pre-payment from-states, so an admin cannot cancel a plain `pending` order even though `PlanTransition` also classifies that as `StudentCancel` — matching design §4.4 Finding 3. `SubmitPaymentAsync` requires the student role, loads state, requires `state.StudentId == userId`, runs the pure reference-string validation, and enforces the authoritative `screenshotPath` check (first `/`-segment must equal the route order id, non-empty remainder) before calling the RPC — a student cannot attach a proof under another order's prefix.

### payment-proofs bucket authorizes read and write by order ownership

`0010` creates the private bucket and both policies keyed off `(split_part(name,'/',1))::uuid`. INSERT is limited to the student who owns the order named in the path prefix. SELECT authorizes three classes — owning student, vendor owner (joined through the order's own `vendor_id` with `v.owner_id = auth.uid()`), or admin — so the vendor-owner branch cannot match a vendor who doesn't own the order referenced by the path. The known limitation (the second path segment is unconstrained, so a student can write multiple objects under their own order prefix) is documented and bounded to the student's own prefixes with no UPDATE/DELETE policy; acceptable for scope.

### Migration split and overload replacement

0009 is exactly the two `add value if not exists` statements and nothing else, so the new enum labels commit before 0010 uses them as a column default and inside RPC bodies. 0010 creates the 4-arg `transition_order(p_id, p_to, p_reason, p_actor)` overload, then `drop function if exists public.transition_order(uuid, text, text)` removes the stale 3-arg version so it isn't left with default PUBLIC/anon/authenticated EXECUTE, and the guarded REVOKE blocks target the new 4-arg signature and `submit_payment`. `ApplyTransitionAsync` threads `actor` after `reason` and before `ct`, `TransitionRpcBody` carries `p_actor`, and the six existing tests plus a `p_actor` body assertion pin the arity change. 0008 re-declares `guard_vendor_columns` with every prior branch preserved (service-role early return, `foodherons.rating_sync` flag, rating/review_count, owner_id) plus the admin-only `approval_status` branch.
