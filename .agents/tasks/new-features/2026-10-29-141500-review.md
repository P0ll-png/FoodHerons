# Admin approval, vendor revenue PDF, and GCash-gated pre-orders

The accumulated branch `feature/admin-revenue-gcash` (3 commits, 29 files, +2083/-139) delivers all three requested features against design.md Revision 4. Admin store approval adds a `vendor_approval_status` enum + RLS narrowing so students only see approved stores, with approve/reject/suspend/re-activate controls on the existing Admin Vendors panel. Vendor revenue export is a pure client-side jsPDF module wired into the dashboard. GCash-gated pre-orders insert two pre-queue states (`awaiting_payment`, `payment_submitted`) before `pending`, with a dedicated submit-payment endpoint/RPC, a private `payment-proofs` Storage bucket, and vendor/admin verify/reject surfaces. The previous review's single finding — `publicVendors` being dead code — is now resolved: Home and Search consume it.

Watch for: nothing blocking. All three gates are green and the one prior finding is fixed (confirmed). The Storage INSERT policy bounds who writes under an order prefix but not how many objects — a known, documented limitation, not new (confirmed).

**Verdict**: APPROVED

## High-level view

Authorization is enforced server-side at two layers, not hidden in the UI. The approval column is admin-only via `guard_vendor_columns` (BEFORE UPDATE) plus the `vendors_select_approved_or_privileged` RLS policy; order state writes go only through the C# order service, which checks role, ownership, and scopes admin cancel to the two pre-payment states. The Storage bucket is private with SELECT/INSERT policies keyed off the order id in the object path. This matches the codebase's "DB owns column privileges, API owns transition identity" split.

The order state machine stays single-sourced. `OrderService.Legal` carries exactly 9 pairs and the SQL `transition_order` whitelist mirrors them; a renamed xUnit sync test (`LegalTransitionSet_matches_sql_whitelist`) pins the two together and passes. No pre-payment state can reach `preparing`/`ready`/`completed` except through `pending`, which is only reachable from `payment_submitted` via a verify move.

The student payment surface resolves the vendor through the full-list `getVendor` (not `publicVendors`), so an order placed against a store that is later suspended still resolves its GCash details. It renders a payment-details-unavailable message when the vendor record or its `gcashNumber` is missing instead of showing a blank destination, and both pre-payment states expose a Cancel control through the single `cancelOrder` handler.

DB changes are confined to the three new migrations (0008/0009/0010); 0001–0007 are untouched. The enum additions live in their own file (0009) because Postgres forbids using a new enum label in the transaction that added it. The palette additions are oranges/yellows/neutrals with no blue.

### publicVendors now consumes through to the student surfaces

The prior pass flagged that `VendorContext` derived and exported `publicVendors` (approved-only) but nothing consumed it, leaving pending/suspended stores visible to admin/owner sessions in the directory and search. That is fixed (confirmed): `Home.jsx` reads `publicVendors` for the directory list, `categoryVendors`, `openCount`, and the hero count; `Search.jsx` reads it for `results` and `popular`. The remaining literal `vendors` occurrences in both files are UI text labels ("No vendors match"), not data reads. `getVendor` and `currentVendorId` stay bound to the full list per the pinned invariant, so the in-flight payment path still resolves a suspended store.

### Server-side authorization across both layers

Approval writes carry no new API endpoint by design; they are plain `vendors` UPDATEs under the admin RLS branch, with the admin-only invariant owned by `guard_vendor_columns` (rejects an `approval_status` change unless `auth_role() = 'admin'`) and the `vendors_select_approved_or_privileged` SELECT policy. Order transitions run through `OrdersEndpoints.TransitionAsync`, which classifies the move (`PlanTransition`) and authorizes per kind: `PaymentReview` for vendor owner or admin, `StudentCancel` for student/vendor owner plus admin only when `plan.From is AwaitingPayment or PaymentSubmitted`. That admin scoping is correct — an admin cannot cancel a plain `pending` order even though `PlanTransition` also classifies that as `StudentCancel`. The submit-payment endpoint requires the `student` role and `state.StudentId == userId`, and additionally validates that a supplied `screenshotPath` starts with the route order id and has a non-empty remainder, so a student cannot attach a proof under another order's prefix.

### State machine single-sourcing

`OrderService.Legal` and the SQL `transition_order` body both list the same 9 pairs; the 0010 migration drops the stale 3-arg overload and applies guarded REVOKEs on the new 4-arg signature, matching the 0007 pattern. The `p_actor` parameter is last, stamping `payment_verified_by` on the verify move. `ValidateTransition` implements the three-bucket reason rule (required for `cancelled`/`awaiting_payment`, forbidden otherwise including the verify move to `pending`), consistent with the UI calling verify with no reason. The sync test and the transition/classification/validation tests pass (108 total, 30 new).

### Payment proof storage boundary

The `payment-proofs` bucket is private. INSERT is limited to the student who owns the order named in the first path segment; SELECT is limited to that student, the vendor owner reached through the order's own `vendor_id`, or an admin — so no vendor can sign another vendor's screenshot. There are no UPDATE/DELETE policies, so proofs are immutable. The documented limitation (the INSERT policy bounds who writes but not how many objects under the prefix, and the filename segment is unconstrained client input) is pre-existing in the design and accepted for scope; only the single path stored on the order row is ever signed and shown.
